# 全量验收 Skill 设计

2026-10-21：基于现行 Skill、既定验收要求及用户对速度的反馈，新增 [v2 设计提案](acceptance-skill-v2-design.md)。v2 尚未替换正式 Skill；下文保留原设计与 Q53 依据。

## 用户目标

2026-10-20 用户要求编写测试 Skill：结合 Computer Use，逐项测试已确认的一百多个决策点，测试后报告问题，交给另一个 Agent 修复，主 Agent 验收。用户随后确认使用“测试数据”。Skill 及配套脚本在项目内实现，不代表已执行全量产品测试。

## 推荐职责

| 角色 | 模型 | 写入范围与交付 |
| --- | --- | --- |
| 主 Agent | 沿当前会话；此前建议 Sol | 锁定验收基准、分批安排、逐项核对证据、复验修复与关联场景，发布最终覆盖报告 |
| 测试 Agent | Luna / max | 按案例操作界面，记录实际结果、证据和可复现问题；不改产品源码或通过条件 |
| 修复 Agent | 另一个 Luna / max | 依据问题单修改指定模块，提交修改依据和影响范围；不能自行把验收项改成通过 |

两个子角色按需轮换，不要求同时常驻。共享本机桌面同一时间仅一个操作者，主 Agent 复验前测试 Agent 交还操作权。

## 覆盖与闭环

- 以 docs/product-decisions.md、docs/acceptance-matrix.md 为唯一产品范围来源，读取全部当前编号规则和 E 系列跨功能流程；每次运行重新提取，不永久写死数量。
- 一条规则可能需要多个子案例。P/W 中范围和工作约定采用文件/产物审查，不用点击伪装软件行为验收。
- 用户可见操作使用 Computer Use；涉及持久化、真实模型、进程、媒体或工具范围的结论，补充对应产物或状态证据。不能以按钮存在、源码存在或 mock 成功代替真实能力。
- Grok 已有界面的视觉核对沿固定版本与窗口条件；品牌差异和额外功能按已批准规则处理，不因反编译中发现功能而扩大范围。
- 每个案例记录基准版本、前置条件、步骤、预期、实际、证据、状态和问题编号。状态沿矩阵：未执行、通过、失败、受阻、待澄清。未实现和缺设备条件不算通过。
- 问题单包含最短复现步骤、预期/实际差异、证据路径、影响编号、版本和严重程度。修复者不能改验收标准掩盖问题。
- 修复后，主 Agent 在对应新构建重新复现，检查关联回归；旧构建的通过证据不能自动沿用到修改后的受影响场景。
- 相同问题连续两轮未解决则保留失败/受阻、报告原因并调整方案，避免无限测试/修复循环消耗额度；不将重试耗尽写成通过。
- 最终逐项汇总全部编号及子案例。所有已定项真实通过前，不发布完整交付结论。截图、日志避免收录认证秘密或无关私人内容。

## 建议存放位置

项目内 `.agents/skills/rambo-acceptance/` 保存 Skill 和必要脚本；测试案例、运行证据、问题单与修复复验记录写入项目 `acceptance-runs/<run-id>/`。大图和私人测试数据不默认提交版本库。Skill 以项目文档为引用，避免复制第二份会漂移的产品规格。

## 已确认：Q53 测试数据环境

用户答“测试数据”，采用独立 Rambo 数据目录和专用测试文件，仍复用 Codex 认证；邮件、删除等案例使用明确的测试对象。真实设备/账号条件缺失时记受阻，不对日常数据故障注入。应用已增加 RAMBO_ACCEPTANCE_RUN 标记校验和 profile/sessionData 分离入口，窗口标题显示验收 run ID；完整运行隔离仍须以实际启动证据验证。

正式 Skill 入口为 [.agents/skills/rambo-acceptance/SKILL.md](../.agents/skills/rambo-acceptance/SKILL.md)，引用现有产品与验收文档。台账脚本负责覆盖、证据摘要、角色分工、版本失效和报告，结论的真实性仍由主 Agent 依据实际观测审核。使用临时夹具验证工具行为；不将这些验证视为产品全量测试通过。
