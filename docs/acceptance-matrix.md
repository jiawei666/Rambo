## 交付原则

用户要求：“不行 我们聊到的所有功能都要能验收”。全部已确认功能均需有可执行操作、可观察预期和实际证据，逐项通过后才算完整交付。实施顺序不缩减最终范围，单个天气/语音流程不构成完整交付。

本文件是**验收规格**；实际执行结果只以对应 run 的台账和证据为准，规格存在不代表功能已经实现或通过。P/W 类含产品范围及工作约定，不将规则数量冒称为独立软件功能数量。明确不做/暂缓项按原决定保留；对尚未定案的建议不自行补成强制功能。

## 使用方式与判定

- 每行对应一个稳定决策编号，必要时为其中各子场景分配 `编号-01/02`，逐个记录，不能用一个成功子场景覆盖整行。
- 执行前记录应用/内置 App Server 版本、macOS 与设备、所用账号能力和工具组件、相关设置。V05/V12 使用用户实际合盖、外接显示器和耳机麦克风环境。
- 执行记录至少含时间、步骤/输入、预期、实际结果、证据路径、结果状态和问题编号。证据按场景选用截图、产物、脱敏日志、thread/run/任务树状态、进程/会话/音频状态；不收录认证秘密。
- 状态仅可为未执行、通过、失败、受阻、待澄清；初始统一未执行。失败/受阻/未执行均不算通过。已确认能力若受版本/账号/组件限制阻塞，须解决或由用户明确改范围，不能自行标不适用。
- 文字说完成、界面有按钮、协议存在、静态包有代码、模拟返回成功，均不能代替相应功能真实完成的证据。受控时钟/故障替身可验证逻辑，但不能代替真实设备、授权、媒体、文件、网络及底层能力闭环。
- 每个未定的实现阈值/格式/视觉基准标明缺口；需要产品选择时再确认，属于技术事项则先调查。缺口未关闭时，不得声称对应整项验收完毕。
