## Q02：上传文件保存副本还是引用原文件

日期：2026-10-19。状态：用户已确认；对应产品规则 F02，并补充 O03 的本机增量备份方式。

问题：上传到聊天或保存为 Bot 长期资料时，保留导入时的副本，还是始终跟随 Mac 上的原文件？

推荐：对应用接受上传的文件，导入为应用管理的本机副本；原文件之后移动、删除、修改不影响已保存版本，更新资料时由用户替换或重新上传。文件夹连接与实时同步另作设计，不将路径引用悄悄当作成功导入。

用户追问原话：

> 这个你觉得怎么样合适呢？我也没有什么想法。你如果都保存副本，会不会比较占用空间？

助手给出的细化建议：只对用户明确上传/导入的附件保存副本，普通本机项目/文件夹操作直接使用原路径；相同内容共享一份实体文件，在多个聊天使用或提升为 Bot 长期资料只增加引用。提供占用查看、大文件查找和无用附件清理，长期资料保留至用户主动删除；每日备份采用增量方式，避免把未变附件完整复制 7 遍。不同内容和不同版本仍占实际空间。

用户确认原话：

> 可以的

结果：上述细化建议已采用，记录为 F02。实现时需保证清理不会破坏仍被聊天、长期资料或保留备份引用的文件；具体备份格式和清理界面仍属实现设计。

补充调查：同一 OpenMausBot 快照对同一上传 ID 的重试复用文件，但不同上传生成新 UUID，未实现跨独立上传的内容去重；已提交附件不按时间自动清理，设置配额并在满额时拒绝新上传。参考实现不能直接当成我们已经选定的存储规则。

补充来源：[上传 ID 与重试复用](https://github.com/milind-soni/OpenMausBot/blob/1da83432c4b952da42225d97fcc623ba754673eb/server/attachments.ts#L355-L383)、[配额和保留说明](https://github.com/milind-soni/OpenMausBot/blob/1da83432c4b952da42225d97fcc623ba754673eb/server/attachments.ts#L16-L27)。

子 Agent 查阅 OpenMausBot 快照 `1da83432c4b952da42225d97fcc623ba754673eb`：受支持的附件上传后保存字节副本；不支持的上传可能回退到 Finder 原路径，因此不是所有文件都复制。上传副本不随原文件变化是根据代码落盘方式得出的结论。该代码不能证明另有 Bot 长期资料库，也不能证明 Grok 的保存方式。

## Q03：首版应用连接是否引入第三方托管连接平台

日期：2026-10-19。状态：用户已确认；对应产品规则 T07。

子 Agent 核对：Grok 应用内连接流程依赖托管的连接器后端；OpenMausBot 一方面支持应用内添加本地命令/远程 URL 的自定义 MCP，另一方面可配置 Composio 项目密钥获得现成应用连接目录。Composio 路线需要额外项目/密钥，服务商令牌由 Composio 保存。自定义 MCP 是否能浏览器授权取决于服务器的 OAuth 支持，不能承诺所有服务统一 OAuth。
