# Rambo 验收 Skill v2 设计提案

日期：2026-10-21。状态：部分实施。现行 Skill 已改为用 Playwright MCP 连接验收 Electron 的 CDP 页面，并通过启动器登记页面 target；Codex 全局 MCP 固定配置为 `@playwright/mcp@0.0.83`，仍需重启 Codex 才能在当前客户端加载新工具。可重复的 Playwright 案例脚本、批量执行器和端到端运行证据仍未完成；本文件其余未实现建议不应视为已落地。原设计和已确认的测试数据约定见 [v1 设计](acceptance-skill-design.md)、[Q53](decision-followups.md#q53)，本轮依据见 [Q54](decision-followups.md#q54)。

## 1. 设计目标与依据

把重复的测试动作交给脚本，把失败诊断、覆盖审查和最终判断交给 Agent。优先连接真实 Electron 开发实例，以页面调试协议完成应用内 UI 操作；按案例需要保留真实系统交互。

这里的“测试”和“验收”不是同义词：

- 单元测试、集成测试、Electron UI 自动化、视觉检查、真实模型 smoke、系统与外部服务检查都是产生证据的**测试方法**。
- 验收是依据稳定产品决策逐条判断“实现是否满足已确认产品与交付条件”的**最终判定**。一条测试通过只证明它实际断言的条件；它不会自动证明整条决策或整个功能域。
- 本 Skill 继续名为 `rambo-acceptance`。内部自动化套件可以叫测试；Skill 的产物仍是覆盖审查、证据、问题闭环和最终交付门槛，不能改名为只表示 CI 测试的 Skill。

| 已有约定 | v2 如何落实 |
| --- | --- |
| P08：所有已确认条件及 E 流程实际通过后才完整交付 | 日常只跑相关回归；最终全量覆盖门槛继续执行 |
| P02：按 Grok 原版证据复刻 | 页面状态、计算样式、尺寸和截图共同核对；按页面及状态记录差异 |
| P01、A01–A05：本机独立应用与自有运行时 | 日常调试真实 Electron、真实 IPC 和指定 App Server；包专属条件在 `.app` 上验证 |
| C01–C07：产品中的真实电脑操作与协调 | 产品 Bot 仍使用既定 Computer Use；测试者连接 Rambo UI 的方式单独选择 |
| Q52/Q53 与 AGENTS：额度、角色、独立测试数据 | Luna / max 测试、另一 Luna / max 修复、主 Agent 复验；按需轮换，所有夹具属于本 run |
| 现有 Skill：版本、证据与失败闭环 | 保留台账、构建 hash/epoch、证据校验、历史失败和逐案例判断 |

[实施进度](implementation-progress.md)记录过 CUA 无窗口/AX、连接超时和停止 UI 链的情况；这说明需要独立于 CUA 的页面验收通道。尚未测得各工具在本项目上的耗时差异，不预设加速倍数。

## 2. 一个入口，三种执行范围

继续使用 `$rambo-acceptance`，从用户请求推导本轮范围，并在计划中明确列出；“全量验收”请求始终选择全量范围。

| 范围 | 触发 | 执行内容与结果边界 |
| --- | --- | --- |
| 快速检查 | 启动确认、调试入口改动 | 确认实例、渲染就绪、连接状态、控制台错误及本次相关小流程；只报告这些观察 |
| 定向回归 | 修复问题、功能批次完成 | 原失败案例、影响依赖、关联 UI/持久化/真实集成案例；由主 Agent 审核选择理由 |
| 全量验收 | 用户明确要求、完整交付前 | 从当前决策和矩阵提取全部义务、补全子案例及 E 流程，关闭全部缺口 |

这里的范围与 `dev/app` 构建模式分开：快速检查也可以检查包启动，全量验收也包含开发模式的逻辑检查。矩阵明确要求最终打包版本、独立安装、系统身份、设备或更新条件的案例，必须在对应环境执行；开发结果按实际模式呈现。

## 3. 按证明对象选择执行方式

先判断一个案例要证明什么，再选择具备该观测能力的工具。复杂规则拆成多个案例组合取证，不用低层通过代替整条规则通过。

| 案例类别 | 默认执行方式 | 必须补充的结果证据 |
| --- | --- | --- |
| 范围/工作约定 | 文件及原始决定审查 | 决定来源、对应产物；只覆盖文档/约定条件 |
| 纯逻辑、数据库、时间边界 | Node 测试或直接调用生产模块 | 真实模块输出、状态差异、边界断言；标注替代的依赖 |
| 应用内 UI 流程 | Playwright 脚本驱动真实 Electron；探索时用已连接的页面工具 | 动作、元素状态、对应持久化/事件结果；需要视觉时保存截图 |
| 视觉复刻 | CDP/页面 API 读取 DOM、计算样式、布局尺寸并截图 | 同条件原版来源、实际截图、逐项差异和审核结论 |
| 模型、工具、邮件、媒体集成 | UI 发起真实操作，结合真实服务/运行时观察 | 关联 thread/run/产物/回执/设备状态；模拟测试另计 |
| macOS、跨应用与真实电脑操作 | Computer Use、系统/进程观察及真实设备 | 实际系统结果、桌面操作或资源释放证据 |
| 安装、包内资源、签名及更新 | 指定 `.app` 或矩阵要求的独立环境 | 包身份/摘要、运行时和系统行为，按包专项案例判定 |

时间边界可用受控时钟覆盖，例如 R02 的 12 小时和 C05 的 30 分钟；还需核对生产默认值和真实调度/资源衔接。受控时钟、模拟媒体或 stub 对话框不证明真实合盖、声音、系统授权和原生文件选择能力。现有 `tests/backend/host.test.mjs` 使用 FakeRuntime，其结果仅证明相应宿主逻辑。

### 3.2 从一条决策生成测试的门槛

每个规则先抽取可观察条件，再选择能证明该条件的最低合理层级；只要规则描述了用户操作或用户可见结果，就仍需对应 Electron E2E：

1. 输入与触发：谁发起、在哪个入口、使用什么数据、是否会创建后台 turn 或外部副作用。
2. 输出与状态：用户看到什么、持久化什么、thread/turn/run 归属哪里、后续轮次如何使用。
3. 边界与拒绝：无选择、多人选择、超时、失败、越权、取消、删除和禁止工具。
4. 时间与恢复：睡眠、错过、重试、不重入、崩溃、重启、更新等待和回滚。
5. 环境与所有权：本机、真实设备、外部账号、包内运行时、不同 Bot 和长期文件引用。
6. 证据组合：确定性测试证明内部条件，Electron/真实集成证明产品路径，最终由主 Agent 按整条决策审核，不能把多个局部通过机械相加而遗漏连接关系。

真实模型、语音和外部服务不适合作为每次提交的快速回归，但最终验收不能只有 fake。推荐每轮日常回归使用确定性适配器覆盖决策分支；稳定候选构建再跑关键真实模型、真实语音、真实邮箱和真实桌面的少量 smoke。所有 fake 必须在证据中明确写出替身旁路和未证明能力。

### 3.3 开发反馈不能与候选交付验收使用同一节奏

业界常用部署流水线解决“要快速反馈，也要全面验证”的矛盾：前级测试快速、范围窄，后级测试慢、范围广，后级不能替代前级。对 Rambo，建议固定为五层；最终验收只落在第 5 层，不能把第 1–4 层每种技术测试都改名叫一次“验收”。

| 层级 | 何时运行 | 包含内容 | 产物与失败处理 |
| --- | --- | --- | --- |
| 1. 提交快速检查 | 每次源码修改 | 类型检查、受影响单元/组件测试、格式或构建错误 | 秒到分钟级；直接修复，不登记产品验收 |
| 2. 功能完成测试 | 一个功能域完成时 | 该域真实 Host/IPC/SQLite 集成测试、关键 Electron 用户路径、跨 Bot/持久化边界 | 留下测试结果；失败建问题并修复，结果不等于产品验收 |
| 3. 定向回归 | 修复或高风险改动后 | 原问题复现、影响依赖、同一断言的自动回归；高风险区域再跑真实模型/设备 smoke | 只重跑受影响层；不得把没覆盖的条件报为通过 |
| 4. 候选版本验证 | 一组功能可交付时 | 全部自动测试、稳定 `.app`、真实模型/语音/邮箱、界面视觉核对、关键用户旅程 | 完整测试报告；慢测试集中此层运行 |
| 5. 发布验收 | 准备给用户长期使用前 | 主 Agent 按 113 条规则和 11 个 E 流程核对真实证据、问题闭环、前置条件和交付模式；少量人工探索补充脚本盲点 | 可留下最终交付判定；任一未执行/失败/受阻/公式缺失均不能报完整可用 |

这套分层的实际含义：

- 单个功能刚改完，不启动全量 113 条复验；先跑能发现该改动问题的快速测试。
- 单元或 fake 集成测试在开发反馈中很重要，但涉及用户可见行为的功能域仍需至少一条真实 Electron 路径，不能只拿代码测试宣布“可用”。
- Playwright Electron E2E 只覆盖高价值用户旅程和跨层连接；边界矩阵放在更便宜、定位更准的层测试，避免把 E2E 变成慢而脆弱的全量按钮回放。
- 真实模型、语音、邮件、外部应用和 macOS 原生能力不追求每次提交都跑；它们在候选版本验证、发布验收及实际失败复现时运行。
- 失败后优先补一条自动化回归；同一问题下一构建由脚本重跑产生的机器结果可作为复验依据。只有脚本盲点、视觉判断、主观体验、真实设备或不可自动断言的结果才需要主 Agent 再实际人工执行一次。
- 全量验收不是每个开发循环都执行的日常测试。用户准备长期使用或要求“全量验收”时，才以候选 `.app` 为目标构建完整跑通；中途的小批次通过只代表这些功能当前可用。

这种方式更接近业界常见的快速反馈、分层自动化和发布前人工把关，也更适合个人产品和 AI 编码的迭代速度。当前 Skill 的“测试者记录后主 Agent 再逐项重做”能提供很强的独立证据，但把这一强度施加给每个小改动会产生大量重复操作；应改为按风险、适用范围和脚本可复现性选择复验方式。

## 4. 调试工具的职责与接入

### 固定执行器，按需诊断

Playwright MCP 已接入，用于探索和操作正在运行的 Electron 页面；读取页面结构、样式、控制台和截图。重复案例仍应逐步固化成 Playwright 脚本，以减少 Agent 往返和保证稳定断言；此类脚本执行器当前尚未实现。每批绑定一个 UI 操作者和一个目标实例；其他工具仅在明确交接后访问该实例。

agent-browser 是可选的 CLI 替代入口，适合批量动作和紧凑输出。先与现有工具做同条件比较，再决定是否纳入默认路径。Electron Debug MCP 作为主进程/IPC 诊断的候选；首轮不要求同时安装多套功能重叠工具。

这些是候选工具分工，不代表当前已连接或兼容性已通过。工具连接失败先核对端口、目标与协议错误；仅在另一工具可证明同一结果且实例身份已复核时切换。执行方式和失败原因进入本轮记录。

### 启动与目标身份

现有 `launch.mjs` 在原有 `RAMBO_ACCEPTANCE_RUN` 校验、profile/sessionData 隔离和 PID 识别基础上增加了验收 CDP。端口固定为 `127.0.0.1:19222`，启动前检查可用性，记录在 `launch.json` 并确认页面 target。固定端口与 Codex 全局 MCP 配置一致；桌面验收按已确认的单 UI 操作者要求串行执行。CDP 只由显式验收启动环境启用。主进程 Inspector 仍只在调查需要时开启，单独登记。

连接后同时核对：run 标记、profile、真实可执行文件/PID、构建 hash/epoch、调试端口及选中的 page target、页面标题中的 run ID、主界面根节点和应用加载状态。仅标题、`/json/list` 可访问、PID 存在或编译成功均不足以证明正确实例已就绪。确认身份后才执行写入操作；健康检查读取现有状态，不靠真实发消息探测就绪。

工具直接连接 Electron 窗口，无需把 renderer 改造成独立网页版。保留 preload 的隔离配置及原有 IPC 校验。渲染进程的 CDP 网络记录未必包含主进程/App Server 的通信；后者使用对应的脱敏进程日志或 Inspector。不得把“未看到浏览器网络请求”当成“没有调用 Codex”。

### UI 操作与状态等待

- 优先使用 role/name 等用户可见语义定位；必要时给稳定控件补 `data-testid`，避免依赖易变 class 和像素坐标。
- 正式 UI 案例从控件发起，执行真实输入、点击、键盘和滚动，检查可见、可操作及结果。直接调用 `window.rambo` 或修改数据库可用于准备夹具和调查，记录为该用途；它们不证明 UI 操作成功。
- 按目标元素、应用事件或任务状态等待，设有界超时；流式聊天不默认等待 `networkidle`，不用固定 sleep 代替完成条件。
- 对可预先确定的步骤批量执行并在关键状态断言，失败即停该动作链并保存现场。随后只继续前置条件未被破坏的独立案例。
- CUA 的焦点/AX 不一致处理沿现有 Skill；CDP 中则核对 target 与页面状态。发送、删除或外部副作用结果未知时，先查状态、任务和回执，不自动重放。

## 5. UI 复刻的专门验收

沿 [界面复刻标准](ui-reconstruction-contract.md) 和 [UI 基准](ui-baseline.md) 为每个页面列出适用的空态、内容态、运行/等待/失败态，以及悬停、焦点、菜单、弹窗等状态。只对产品范围内适用状态建案例。

固定参考版本、窗口/视口、设备像素比、主题、字体条件和可控内容。原版来源包括已有反编译/资源证据与可获取的真实截图；原版无法连接 DOM 时如实使用已有来源，不预设原版支持 CDP，也不操作原版私人聊天来准备样本。

每个视觉案例保存：基准引用、Rambo 实际截图、关键元素布局/计算样式、差异说明。具备可比基准时输出差异图。像素指标用于定位差异，不能单独证明 P02；既定品牌差异单列，已确认新增功能标出继承的原版组件依据。

时间戳、模型流式正文等动态内容可在静态对照中受控或局部遮罩，但要保留原图、遮罩范围和理由；被遮罩内容的显示与交互另有案例。动画行为另验，不能靠全局关闭动画后声称已验。没有原版证据的页面保留缺口；不自行设一个宽松相似度门槛通过。

## 6. 批次、角色与修复节奏

1. 主 Agent 冻结范围和基准、审查子案例及证据需求，按功能域/共享前置分批。已执行的正常状态可作为同批后续前置，互相污染的删除/故障分支用独立对象。
2. 测试 Luna / max 在固定实例执行整批脚本或探索流程，逐案记录真实结果；源码只读。一次返回失败摘要、复现、原始证据和覆盖缺口，减少逐案例交接。
3. 另一 Luna / max 按问题单集中修复相同代码区域，提交根因、修改、影响案例和必要实现检查；不改变通过标准或登记验收通过。
4. 测试者在新构建复测。主 Agent 审核覆盖及原始证据，并独立执行本批案例/修复场景与关联回归，取得新的记录后 `verify`。可复用确定的脚本，但须审核断言来自产品标准，并防止“准备数据已直接制造预期结果”；只阅读测试者报告不算复验。
5. 同一缺陷连续两轮修复仍失败，转入新的根因调查，保留问题和受影响案例状态；其他独立批次继续。工具/环境没有变化时停止重复连接或盲点。

同一测试实例（包括 CDP）只有一个 UI 操作者。应用自己的 Computer Use 调度案例，还要确保测试操作者不抢占正在验证的真实桌面；并发请求和 FIFO 由案例安排，不能让测试工具代替 Bot 完成电脑动作。独立数据与进程的纯逻辑检查可并行，仍受 Q52 的额度安排约束。

## 7. 构建、复验与全量交付

继续采用当前保守的 epoch 规则：一批源码修改结束后登记新构建，重启验收实例，旧 epoch 结果保留为历史、待重验。日常定向回归仅执行受影响案例，报告同时列出其他待重验项；完整交付前在最终目标构建完成全部适用案例。

不在首轮设计依赖图缓存来跨构建自动继承通过状态。这样避免因依赖推断漏项而放宽现有门槛。文档约定、开发逻辑和打包运行分别保留实际环境身份；开发检查可作为辅助证据，不能自动转换为 `.app` 通过。需要混合构建模式时，明确每个规则在最终交付中所需的证据，不因切换模式套用旧结果。

一批集中改动后重新登记 epoch；交付全量阶段以稳定候选构建运行，出现修复则生成新 epoch、安排对应复测和最终全量运行。减少反复手动操作的主要方式是脚本与批处理，不能靠省略旧构建失效条件提速。

## 8. 台账和证据设计

复用现有 `run.json`、`cases.json`、`issues.json`、`audit.jsonl`、`REPORT.md`、`record/verify` 与证据 hash 校验。一个实际流程可关联多个规则，逐规则写清覆盖条件；规则行、E 流程、子案例与脚本断言数分别统计。

建议增加的执行元数据：`executor`、工具版本、`testScriptHash`、`attemptId`、目标 PID/page target、构建/epoch、开始/结束时间、mock/真实服务说明、前置对象 ID、实际断言和证据索引。测试者和主 Agent 使用不同 attempt 和证据文件。

当前 `ledger.py` 的 `plan` 只保存已定义字段，任意新增 JSON 字段不会自动持久化。首轮把上述元数据写入 `evidence/<case>/<attempt>/execution.json`，随实际日志/截图一起登记为证据；需要脚本强制校验或汇总时，再显式扩展 schema 与 CLI。执行脚本、Skill 和工具版本单独记录摘要；当前产品开发指纹没有覆盖整个验收执行代码，不能仅靠产品 hash 证明执行器没变。

证据按案例需求生成：逻辑案例保留输出和断言，UI 案例保留动作与元素结果，视觉案例必须有图像，真实集成保留关联回执或产物。正常路径在关键检查点取证；失败时采集目标截图、结构、控制台与相关日志。不在每次点击后输出整屏和全部日志。

测试数据及外部动作沿现有 Q53：唯一 run 标记、专用 profile/夹具、明确测试邮箱和收件人；不复制认证秘密、不登出用户日常账号，不用日常数据做故障注入。主进程/IPC 日志只收相关事件与必要字段，避免捕获凭据和完整媒体协议。

错误区分产品失败、环境/工具受阻和规格待澄清，但结果状态仍沿现有五种值。工具断开不证明产品失败；产品未实现不能仅因为工具错误被改记为通过或略去。恢复后同一案例追加新尝试，保留原失败/受阻。

## 10. 实施顺序与方案验收

1. **先打通连接**：在独立测试 profile 启动 Electron，核对 CDP 目标、读取页面结构/控制台并保存真实截图，验证重启后重新绑定。此步只证明调试通道可用。
2. **固化一批已有流程**：选择 B04 创建、B07 管理、T06 权限覆盖等已具备入口的具体子案例；按实际实现拆解，不默认整条规则可通过。增加取消/错误分支和测试者/主 Agent 两次执行记录。
3. **补视觉与真实集成**：选有真实 Grok 基准的页面完成 P02 的窄案例；再为聊天等接真实 App Server 与产物证据。缺失能力正常报失败/受阻。
4. **替换正式入口并扩展全量**：同步 Skill、手册、启动器、元数据和角色交接，再逐功能域补齐所有义务，保留系统/设备/打包专项。

在同一源码/构建模式、相同独立夹具初始状态和同一组场景下，对可用的 CUA 路径与新路径记录：准备耗时、执行耗时、AI 工具调用数、人工接管、重试次数、证据完整性和错误检出情况。CUA 不可用时只报告新路径测量值及原阻塞，不捏造速度对比。工具启动和首次冷启动与重复运行分开统计。

设计实施后的验收条件：能识别错目标并在写入前停止；断言失败能保留现场；测试者结果与主 Agent 复验分离；正常、取消和失败分支有真实结果；变化后的构建/脚本不会复用失效证据；没有外部条件时准确受阻；报告保留所有未覆盖义务。仅这些执行机制通过，仍不等于 Rambo 产品全量通过。
