# Rambo 分层测试与发布验收

目标是让每个已确认条件都有能证明它的真实结果，并让日常反馈尽量快。实现范围来自项目文件，不以本 Skill 另造产品规格。用户已选择使用**独立测试数据**。

先把请求归入以下层级，不把每次开发测试都叫全量验收：

| 层级 | 命令或触发 | 产物边界 |
| --- | --- | --- |
| 快速检查 | `npm run verify:fast` | 类型、后端测试、规则目录和台账脚本；不登记产品通过 |
| 功能完成 | `npm run verify:feature -- --rules ...` | 当前功能规则的有效测试证据；可报告“功能当前可用” |
| 定向回归 | `npm run verify:regression -- --issue ...` | 原问题及影响范围；不证明其他规则 |
| 候选版本 | `npm run verify:candidate` | 全部自动测试、稳定 `.app` 和必要的真实依赖 smoke |
| 发布验收 | `npm run accept:release` | 113 条规则、4 条核心旅程和发布套件完整审核 |

`tests/acceptance/catalog.json` 分成两层：`ruleAcceptance` 保存每条规则的完整用户场景、断言、证据要求和剩余工作；`cases` 只登记能产生局部证据的测试。两层不能混用。当前顶层边界是 4 条用户旅程 J1–J4 和 6 个发布套件；11 条 E 流程仅作为历史组合映射。

`tests/acceptance/rule-plans.mjs` 是 113 条完整场景的来源，`docs/acceptance-test-plan.md` 是可读计划。现有案例通过不等于整条规则通过；例如后端断言只能证明它实际检查的持久化或协议边界，不能替代真实 Electron、Live、外部服务或系统结论。

## 开始与分工

1. 定位同时含 `docs/product-decisions.md`、`docs/acceptance-matrix.md` 的 Rambo 项目。读取其 `AGENTS.md`、上述两份文件以及本次相关的 UI 基准、实施进度。范围/约定规则用文件审查；实际功能用运行测试，不能把规则数冒称独立功能数。
2. 默认以 Electron Vite 开发模式验收，记录 App Server 版本、Electron 版本、macOS、设备和本轮能力。仅当案例明确要求独立安装、签名、包内资源或更新行为时使用 `.app`。用 [台账脚本](scripts/ledger.py) 创建或登记对应模式的 build；通过 [启动器](scripts/launch.mjs) 启动后，Playwright MCP 连接本机 CDP 页面；指令见 [运行手册](references/workflow.md) 和 [UI 调试手册](references/ui-debugging.md)。
3. 主 Agent 保持覆盖审查和最终发布权。独立测试者和修复者按风险启用，不要求每个自动测试固定产生两次人工操作。人工界面、真实设备、外部副作用和结果无法自动判定的案例仍须独立观察与主 Agent 复验。
4. 修复者仅改指定源码、必要实现测试及修复记录，不能改通过标准。确定性的自动结果可由主 Agent 审核断言来源、脚本 hash、构建 hash 和证据后用 `machine-verify` 登记单次通过；其他案例继续用 `record` 与 `verify`。

## 测试数据和环境

- 所有测试产品数据放 `acceptance-runs/<run-id>/profile`，文件放 `fixtures`，证据放 `evidence`。默认用 [启动器](scripts/launch.mjs) 以 `npm run dev` 启动，并通过 `RAMBO_ACCEPTANCE_RUN` 指向本轮目录；通过 `launch.json` 和 Playwright MCP 当前页面核对本轮 run、PID、profile、构建及 target 后，才创建或删除测试数据。日常 Rambo 目录不能作为故障注入/清理目标。
- 每批源码修改完成后登记一次开发模式指纹，再重启验收实例；同一批中不要每改一处就打包。源码变化会使旧指纹和旧 epoch 失效。只有包专属案例才构建和启动 `.app`。
- 目录隔离只分开产品数据，不是 Full Access 下的文件权限沙箱；测试任务仍须明确使用本轮夹具，不改变既定权限产品规则。
- 可以复用既有 Codex 认证，但不复制凭据、不把它们导出或截图。复用认证不是授权退出/修改原生客户端登录；A03 未登录场景须单独的认证环境，不能登出用户日常账号来制造。
- 邮件仅用明确提供的测试账号/收件人和本轮唯一主题标记。没有指定就将相应用例记受阻；不发给未知地址、不将真实邮件当可删除夹具。
- 删除、崩溃、备份恢复、版本替换等只针对已登记的测试对象和本应用拥有的进程。真实合盖/耳机、系统授权或账号条件缺失时记受阻，列出需要用户配合的具体动作；不声称机器睡眠时已通过。
- 完整测试条件和夹具规则按需读取 [案例与证据约定](references/cases-and-evidence.md)。

## 逐项执行

1. 从矩阵核对全部规则，再从 `ruleAcceptance` 读取该规则的完整场景；现行报告按 J1–J4 和发布套件汇总，历史 E 编号只在旧 run 中保留映射。**一条规则场景是验收义务，`cases` 中一条通过测试仅证明局部条件。** 检验场景是否覆盖正常、拒绝/取消、失败、恢复、持久化和跨 Bot 边界；主 Agent 审核后才能登记规则级结果。
2. 按功能域及共享前置组织批次，一次派测覆盖该批多个案例；能共用同一启动窗口和测试夹具时就复用，减少重复启动、准备和 Agent 交接。纯文档、源码/后端检查可在不争用共享状态时并行；桌面操作始终串行。逐案例留证和判定，不把批次成功当成整批通过。批内某项失败时，先记录问题并继续不受影响的案例；按同一代码区域集中修复，再登记一次新开发 epoch。具体批次安排见[运行手册](references/workflow.md)。
3. 按证明对象选择最低成本但足够强的测试：纯逻辑和状态转换用单测；Store、Host、IPC、权限和跨对象边界用真实集成测试；高价值用户旅程用 Playwright `_electron.launch` 脚本操作真实 Electron；Playwright MCP 用于探索 locator、读页面和诊断失败；Computer Use 只处理 macOS 原生、真实设备、跨应用和产品 Bot 的实际电脑操作。可重复页面案例不逐步由 Agent 通过 MCP 回放。只有打包、安装、签名、Voice、邮件、系统通知和真实设备等必要条件出现时，才运行慢测试。不要另开普通浏览器访问 renderer URL，也不要直接调用 `window.rambo` 或改数据库来冒充 UI 通过。
4. 视觉以同版本 Grok 的实际页面、尺寸、主题和反编译来源对照；既定 Rambo 品牌差异单列。不要操纵原版的真实聊天/连接；原版证据不足就保留缺口。
5. 每个结果记录实际步骤/输入、预期、实际、构建、时间、证据和问题编号。点击成功、按钮出现、协议存在、源码存在、mock 返回均不能代替真实结果。没有实现记失败；缺外部条件记受阻；产品标准确实缺失才待澄清。

## 报问题、修复、复验

- 测试 Agent 创建问题单，附最短复现、预期/实际、影响编号、严重程度、构建和证据。提供给修复 Agent 的是这些事实，不强制猜测的根因。
- 修复 Agent 回报修改文件、根因、影响范围、构建与必要实现测试结果。不能改测试条件以让产品过关，也不能把自己的修复声明写成验收通过。
- 主 Agent 对新开发指纹或包构建登记 epoch，核对受影响规则与回归范围。确定性自动测试在该构建上重跑并登记机器证据；人工、真机和外部副作用取新的独立观察。台账默认使旧 epoch 的通过失效，保留历史。
- 同一缺陷连续两轮修复仍失败，停止重复尝试，保留失败/受阻并报告原因，换调查方向；未解决不算通过。
- 工具/组件不能使用时先查实际错误。界面受阻可继续非界面案例和缺陷修复；不能用假截图或静态代码替代未执行部分。

## 完成与交付

运行脚本生成 `REPORT.md`，汇总全部规则、J1–J4、发布套件、规则场景、局部测试案例、未执行/失败/受阻/待澄清、开放缺陷和修复复验链。每条由主 Agent 审核；脚本检查覆盖与证据完整性，不能代替人判断证据是否证明预期。

进度更新同时区分规则行、规则场景、局部测试案例和 J1–J4；标明当前 epoch 的通过/失败/受阻/未执行数量，并把历史 epoch 结果单列为待重验，不把旧记录说成当前通过，也不把 epoch 切换后的当前计数归零说成此前没有做过。

只有全部已确认条件在目标构建上实际通过、开放缺陷与阻塞关闭，才能报完整交付。否则交付真实部分结果和剩余问题，不删减用户已经确定的范围。技能本身的结构验证、脚本单测或受控演练不等于产品全量验收通过。
