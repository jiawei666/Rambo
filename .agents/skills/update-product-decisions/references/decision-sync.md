# 决策同步手册

## 当前文件职责

| 文件 | 当前职责 |
| --- | --- |
| `docs/product-decisions.md` | 唯一现行产品准则；稳定编号；历史只保留明确的取代说明 |
| `docs/decision-followups.md` | 用户原话、确认回复和后续依据；使用 `<a id="qNN"></a>` 锚点 |
| `docs/acceptance-matrix.md` | 每条现行规则的用户操作与可观察通过条件 |

| `docs/implementation-progress.md` | 当前实现边界，不替代产品决策或验收通过 |

## 有效依据

有效的新决策依据只有：

- 用户在本轮主动调用 Skill 时写下的新要求；
- 用户明确认可并指向的工作区改动；
- 与该要求直接相关、可读取的产品证据。

以下内容不自动成为新准则：

- 助手推荐；
- 代码现状；
- 测试通过；
- 参考产品行为；
- 历史对话中未获确认的提议；
- Agent 自己做出的实现取舍。

## 编号与历史

同一产品对象的修订沿用原编号。验收矩阵、测试场景和 run 历史都依赖稳定编号，重新编号会断开证据。

现行表格删除被替代的正文。历史文件可以继续保留旧原话和旧方案，但必须明确说明它已被某编号的新决定取代。不要让搜索同一编号时同时返回两段互相冲突、且都像现行要求的文字。

新增独立规则时才分配新编号，并同时加入：

- 产品决策表格；
- 验收矩阵；
- 规则计划；
- 至少一个现行旅程或发布套件；
- 对应局部测试入口或真实 `not_implemented` 缺口。

## 常见边界

### 用户给出新要求，代码还未改

先更新现行准则与验收标准。实现缺口写入 `remaining` 和局部案例的限制，不把规则写成已通过。

### 代码已改变，但用户没有表达新的产品选择

只更新验收判断中受新行为直接影响的局部断言，不把实现取舍升级为产品规则。若必须改变产品承诺，停止并要求用户确认。

### 一项新要求影响多条规则

逐条证明直接冲突。例如改变执行状态的展示方式可能影响 B11 与界面规则，但不会自动改变记忆、权限或路由规则。共享术语不要批量替换成新语义。

### 删除旧要求

从现行矩阵和规则场景里删除旧断言，同时保留其历史来源。相关局部案例如果仍能证明其他规则，只移除错误归属；如果只证明旧要求，更新或标记为具体缺口。

### 旧验收 run

不修改已登记 run 的历史 hash，也不把旧 epoch 结果重新解释为当前通过。决策或矩阵 hash 改变后，用项目台账登记新基准；旧证据保留为历史。

### 证据链接

决策依据优先指向 `decision-followups.md` 的稳定锚点或 `conversation-evidence.md` 的 M 锚点。新增 Q 条目沿用现有 `<a id="qNN"></a>` 形式；编号取当前最大 Q 加一，重复标题锚点不要复用。

## 失败处理

- `test:catalog` 报规则编号不一致：先修决策或矩阵的现行行，不删除脚本校验。
- 标题、步骤或期望不一致：以矩阵为可读来源，按 `test:catalog:sync` 刷新目录；不要手改生成字段。
- 规则没有旅程归属：把它加入确实覆盖该规则的旅程或发布套件。
- 测试名不存在：实现新行为后登记真实测试，或保留具体的 `not_implemented` 缺口。
- 旧证据与当前决策冲突：标为历史失效，不用它证明新规则。
