# 更新 Rambo 产品决策与验收

只在用户主动调用本 Skill 时执行。调用即授权把用户提供的新要求或当前工作区最近改动提升为产品决策；普通实现、修 bug、代码审查和建议不自动获得这个权限。

目标是让项目里只保留一套现行的、可执行的准则。用户的新要求高于旧决策、旧建议和现有实现；旧实现不能反过来限制新决策。

## 1. 建立改动与规则的对应关系

1. 读取 `AGENTS.md`、`docs/product-decisions.md`、`docs/acceptance-matrix.md` 和 `docs/decision-followups.md`。
2. 如果调用中给出了新要求，以该要求为准，并用它定位受影响的规则；调用文本不足以确定边界时先只问一个最关键的问题。
3. 如果调用没有给出新要求，读取当前工作区相对 `HEAD` 的已跟踪改动；未被忽略的新文件也纳入。若 `HEAD` 不存在，则以本轮实际编辑过的文件为主，不把全仓未跟踪文件都算作本次改动。无可用改动时停止并要求用户指定范围。
4. 对每项受影响规则，读取它在矩阵、`tests/acceptance/rule-plans.mjs` 和 `tests/acceptance/catalog.json` 中的对应内容。读取相关的 UI 基准、技术设计、实施进度和证据章节。
5. 只修改能被新要求或改动直接证明冲突的准则。相邻规则、共享术语和未展示的排除项保持原样。语义边界不清时停下来向用户说明候选冲突，不自行扩大授权。

完成条件：每项打算修改的现行规则都有具体改动依据；每项保持原样的相邻规则都有不修改的理由。

## 2. 先形成替换清单

写文件前先给出并核对这份清单：

- 新要求或改动依据；
- 新增、修改或删除的规则编号；
- 将被替换的旧准则摘要；
- 受影响的矩阵行、规则场景、catalog 条目和证据；
- 仍然有效、不得误删的相邻条件。

用户已经在调用中明确授权直接更新，且清单边界没有歧义时，可连续完成后续步骤，不再逐项等待确认。编号默认保持稳定；新准则覆盖同一产品对象时沿用原编号，不重新编号。只有用户明确要求新增独立准则时才使用新编号。

## 3. 写入唯一的现行决策

更新 `docs/product-decisions.md`：

1. 在同一编号的现行表格行中写入新准则的完整正文，删掉被它替代的旧正文。不要把旧规则继续留在现行行里“同时有效”。
2. 更新依据链接；用户原话和改动说明写入 `docs/decision-followups.md` 的新 Q 条目或对应既有条目，保持锚点可解析。只记录用户要求、授权和必要技术事实，不把助手建议写成用户决定。
3. 在文末变化记录或对应章节说明中保留一句精简的取代记录：日期、编号、被替代内容类别、当前依据。历史问答文件继续作为审计记录；现行表格只表达一套规则。
4. 检查同一文件其他地方是否仍把旧规则写成现行要求、未定事项或实现前提；直接冲突的重复说法要同步修正。历史说明明确标注为历史时保留。
5. 新要求涉及原有“尚未定案”或“技术验证”项时，将它从待决状态提升为现行规则；不能仍留在待决清单里与现行表格并存。

完成条件：按稳定编号检索时，现行决策只有新准则；历史只以明确的“已被取代”记录存在。

## 4. 同步验收层

按顺序更新：

1. `docs/acceptance-matrix.md`：让该规则的操作与通过条件反映新准则。移除不再要求的旧断言，补上新要求的可观察结果，但不添加无证据支撑的实现承诺。
2. `tests/acceptance/rule-plans.mjs`：更新完整规则场景的步骤、预期、证据和 `remaining`。场景必须能区分新旧准则，不能只把矩阵整行原样复制。
3. `tests/acceptance/catalog.json`：只在确实需要时手工修改局部案例；完整场景由目录生成脚本维护。旧案例若仍在验证被撤销的行为，要更新断言或标为具体缺口，不能继续算作当前通过。
4. `docs/acceptance-test-plan.md`：通过 `npm run test:plan` 重新生成，不直接编辑生成结果。
5. 保留 `catalog.json` 中不相关案例、旅程归属和发布套件归属。改变规则范围时同步分组，不能只改规则正文。
6. 如果现有测试、证据、验收 run 或实施记录把旧准则写成当前预期，同步改到新准则；旧 run 只能保留为历史，不能继续作为当前构建通过证据。

完成条件：决策、矩阵、完整场景、局部案例、旅程/发布套件归属和证据入口都描述同一套现行规则。

## 5. 执行一致性检查

用项目脚本验证，不手写结论：

```sh
npm run test:catalog:sync
npm run test:plan
npm run test:catalog
npm run typecheck
```

如本 Skill 的检查脚本存在，再运行：

```sh
node .agents/skills/update-product-decisions/scripts/check-decisions.mjs
```

任一命令失败就修复结构性问题。不要通过削弱校验、删除测试或改成 `not_implemented` 来制造通过。代码还没实现的新准则可以保留真实实现缺口，但决策和验收标准必须先一致。

完成条件：相关命令结果可复现，且没有生成文件与源文件不一致。

## 6. 报告实际结果

完成后向用户报告：

- 哪些规则编号已更新，以及新旧准则的关键差别；
- 决策、矩阵、规则场景、catalog、证据和实施记录中实际改了哪些文件；
- 哪些旧验收结果因准则变化而失效；
- 哪些实现或测试仍是缺口；
- 实际运行的检查命令和结果。

产品准则更新完成不等于功能验收完成。不要把文档一致、类型检查或局部测试通过写成对应规则已通过。

详细格式、证据锚点和常见边界见 [决策同步手册](references/decision-sync.md)。
